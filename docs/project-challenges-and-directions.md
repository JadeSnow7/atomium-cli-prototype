# Atomium 当前挑战与可能方向

讨论稿 · 2026 年 11 月 26 日 · 基线为 `main` 的 `a4ae5f4`

Atomium 已经能让本地命令行 Agent 在受限环境中修改一份工作副本，再由用户审阅并导出。项目面临的核心挑战，是把几项分别成立的能力放进同一次真实工作中：用户知道工具能读什么、能把数据发到哪里、谁放行了例外，也能在任务结束后核对写回宿主的改动。这个基础可以服务开发者、桌面 AI 用户和企业安全团队，但他们愿意承担的使用成本、需要的证据和付费理由各不相同。

## 当前能力及其适用范围

| 能力 | 已有实现或实测 | 影响使用的边界 |
| --- | --- | --- |
| 运行隔离 | 正式守护进程 `atomiumd` 用 macOS Seatbelt 限制子进程，设置独立 HOME 和临时目录。默认策略拒绝访问宿主钥匙串。 | 子进程仍使用守护进程的系统账户。独立 Box 账户和独立系统服务尚待接入正式启动流程。 |
| 出网与审计 | 每次运行有独立网关。网关逐个检查明文 HTTP 请求，支持主机白名单和中断在途连接。 | 目前依赖上游代理，无上游时拒绝转发。HTTPS 隧道建立后正文不可见。按目的地展示放行、拒绝和流量记录是 v2 规划能力。 |
| 凭据与并行 | 加密凭据库支持 OAuth 凭据的封存和刷新写回。两个不同的 `agy` 订阅曾实测并行且未串号。 | 在文件投影模式下，工具能从自己的运行目录读取真实凭据。同一 OAuth 订阅当前独占使用。 |
| 工作区与审批 | Broker 支持导入、冻结候选改动、审批导出、基线冲突检测和中断恢复。 | 同一工作区同时只允许一个写入者。审批记录保存了决定，当前协议无法证明是用户本人确认了这一次操作。 |

PR #4 已合入，协议 v1.2 是当前实现。已有自动化回归覆盖 macOS、Linux 和跨层流程；合并验收将个人钥匙串捕获、真实 Box 账户的创建与销毁列为后续手工核验项。v2 已有设计，Box、Session 和 Grant 等对象仍按里程碑落地。[开发状态](../DEVELOPMENT-STATUS.md) · [协议及实现范围](protocol-v2.md) · [PR #4 验收](https://github.com/JadeSnow7/atomium-cli-prototype/pull/4)

## 影响路线选择的挑战

### 隐私承诺取决于实际启动方式

同一个宿主剪贴板标记，在 S2 原型中出现了两种结果：沿用宿主图形会话启动时能读到，切换到独立 Box 用户的服务环境后读不到。终端授予的截屏、麦克风等系统权限也受启动链路影响。与此同时，正式 Seatbelt 已经有自己的钥匙串和硬件信息限制。今天阅读隐私矩阵的人，很难从“已强制”判断自己的启动方式获得了哪一层保护。一项可供用户依赖的结论，需要对应到具体系统版本、正式入口和可重复观察的结果。[S1 与 S2 原型说明](prototypes/s1-native-gui-box.md) · [产品规格 §6](product-spec.md) · [正式 Seatbelt 策略](../crates/atomium-runtime/src/macos_seatbelt.rs)

### 放行出网和证明本人同意是两件事

今天启动运行的客户端可以提交上游地址和目的主机名单。未来即使把两者换成策略 ID，仍需回答：谁能给 Box 绑定或修改策略，启动会话的人能否选用更宽的授权？直连解决普通用户没有上游代理时的可用性，同时也把核对实际连接地址、执行拒绝、记录决定的责任交给本机网关。企业强制经上游代理和个人开箱直连，需要不同的部署验证。[当前网关启动路径](../crates/atomiumd/src/lib.rs) · [网络能力基线](../DEVELOPMENT-STATUS.md)

控制面目前依赖仅同一系统用户可访问的 socket。M5 计划识别可信客户端，M7 计划用 Touch ID 或设备签名把本人同意绑定到具体操作。两者之间存在产品问题：哪些动作可由已授权程序完成，哪些必须等用户看到目标和范围后才能生效？审批过密会打断工作，审批过宽又会让用户难以解释自己授权了什么。[协议 §2、§3、§6](protocol-v2.md)

### 凭据隔离和工作副本分别限制并行

设想两个 Agent 在同一项目上各修一次故障，用户要比较两份结果。如果两者共用一份 OAuth 订阅，宿主需要统一管理凭据注入与刷新，并验证工具在真实登录和续期时仍可工作。如果两者都要写代码，每个会话还需要自己的副本；第一份结果合并后，第二份如何展示基线变化，也会影响审阅体验。验证注入看凭据归属与刷新，验证协作看候选差异和冲突。任一项通过，都只解决演示中的一部分。[订阅实测](subscription-quickstart.md) · [工作区租约与导出语义](protocol-v2.md)

### 桌面应用路线改变了部署成本与许可问题

S1 在 macOS 26.6.2 上验证了跨用户原生窗口方案的局限，项目已把 macOS GUI 旗舰转向 L2 Mac VM。虚拟机有自己的桌面环境，也把启动时间、内存、磁盘、登录和文件交换带进日常体验。产品规格的 Pro 清单和企业风险应对仍列有 L1-GUI，与已经记录的技术结论冲突。[S1 结论](prototypes/s1-native-gui-box.md) · [产品规格 §3、§10、§12](product-spec.md)

macOS Tahoe 许可 §2B(iii) 在其适用条件下，允许在每台自有或受控、已运行相应系统的 Apple 品牌电脑上运行最多两个额外虚拟实例。条款分别列举软件开发、开发中的测试、使用 macOS Server、个人非商业用途。客户在自己的 Mac 上做软件开发、员工在 GUI 中处理日常办公材料、厂商托管供他人访问，涉及不同的使用方式。对外承诺 L2 支持某类部署前，需要针对该场景确认适用条款。[Apple macOS Tahoe 软件许可 §2B 与 §3](https://www.apple.com/legal/sla/docs/macOSTahoe.pdf)

## 四个可以分别验证的产品方向

现有规格选择了先在中国以中英双语开源获客，再面向全球企业变现；macOS GUI 已选择 L2。仍待判断的是第一批持续使用者是谁，以及开源使用者的需求与企业采购理由有多少重合。下面四个方向可以共享底层能力，各自需要不同的使用证据。[产品决策与商业假设](product-spec.md)

| 可能方向 | 用户为什么会用 | 可用来判断的证据与代价 |
| --- | --- | --- |
| 研发团队的 CLI 工作区 | 开发者愿意让 Agent 处理真实仓库，因为能限制文件和网络访问，并在写回前看清改动。 | 用一个真实 CLI 走过安装、登录、受控联网、审阅和导出。观察开发者第二次是否主动使用，以及哪些审批或兼容问题让他退回普通终端。 |
| 面向桌面 AI 用户的隐私工作区 | 用户想拿一份敏感文档使用熟悉的桌面应用，同时控制文件和剪贴板交换。 | 在目标 Mac 上完成一次真实文档任务，记录从启动到可用的时间、资源占用和交换文件的步骤。个人使用与企业办公分别评估部署条件。 |
| 多 Agent 实现与交叉审阅 | 工程师希望比较两个工具的改动，或让另一个模型发现遗漏，同时看清每份结果的来源。 | 用独立工作副本，对同一任务比较单 Agent 和多会话流程。计入人工核对、冲突处理和订阅成本，观察总合并时间和实际发现的问题。 |
| 企业跨端策略与审计 | 安全管理员需要在不同设备上执行同一条组织规则，解释一次例外，并把证据交给审计方。 | 由目标团队提供一条现行规则和所需证据格式。在两种目标执行端核对放行、拒绝、撤销与审计结果，并确认谁拥有部署权限和采购预算。Windows 执行端及企业管理能力仍在后续规划中。 |

应用画像目录是四条方向都可能用到的资产。一份画像描述应用如何安装、登录、联网，以及哪些行为能检查。它能否形成长期优势，取决于第二个应用能复用多少工作，以及供应商更新后能否及时发现兼容性退化。对启用证书锁定的应用，域名级控制和正文检查需要分别说明。维护成本、可支持的应用数量和用户愿付的价格仍需真实使用来衡量。[应用画像与兼容性假设](product-spec.md)

## 留待讨论的取舍

- **一个应用做多深，几个应用才算可复用？** 单个 CLI 的完整任务能暴露登录、授权、导出之间的问题。扩到第二个乃至规划中的四个画像，才能看出哪些是通用能力。两类证据回答不同问题。
- **何时调整运行时代码结构？** 当前启动入口集中处理租约、凭据、进程启动与收尾。先做等价拆分，有利于复用 Session 的生命周期；随真实会话逐步抽取，则可以少猜一层接口。比较两种做法时，应关注取消、失败与恢复行为能否保持一致，以及何时能获得第一份用户反馈。[当前启动实现](../crates/atomiumd/src/lib.rs)
- **第一批用户的哪种行为值得继续投入？** 开发者主动复用、桌面用户接受 VM 体验、审阅者发现了原流程漏掉的问题、企业管理员愿意给出试点设备和预算，分别支持不同方向。一次演示成功可以说明技术可行；哪个场景值得成为产品重心，仍取决于目标用户在真实约束下的选择。
